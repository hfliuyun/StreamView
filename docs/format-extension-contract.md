# StreamView Format Extension Contract

Status: accepted project contract. This English document is normative; the
[Chinese companion](zh-CN/format-extension-contract.md) is maintained for
accessibility. Read this document before changing support for a new container,
codec, elementary stream, or media sub-format.

## 1. Scope

This contract applies whenever a change adds or expands a user-visible media
format, including:

- a new elementary stream or codec;
- a new container or file family;
- a new detector, scanner, entry point, or cross-layer payload view;
- a new official rule package or a new package entry point; and
- a change to an existing format's accepted syntax, diagnostics, fields,
  framing, navigation, or advertised coverage.

The task is complete only when the implementation, specification, tests,
verification evidence, and implementation-plan record are all present.

## 2. Required Order

Agents must follow this order. A later step cannot substitute for an earlier
one.

### Step 1: Classify the format

Write down whether the target is:

- an elementary stream or a container;
- length-delimited, sentinel-delimited, or chunk/box-delimited;
- a codec payload, transport format, or both; and
- a format-specific entry point or a cross-layer payload selected by an
  existing container.

For a format such as WAV, explicitly decide the RIFF/WAVE container scope,
supported chunk types, alignment rules, codec families, and postponed
features such as RF64 or compressed WAVE variants. Do not infer these choices
from a filename extension.

### Step 2: Specify before coding

Before changing C++ or `.svfmt` files, create a consecutive bilingual ADR:

```text
docs/adr/NNNN-<format-or-decision>.md
docs/zh-CN/adr/NNNN-<format-or-decision>.md
```

The ADR must state:

- the normative specification, edition, and clause references;
- package ID, entry-point ID, format identifier, and initial package version;
- detection and arbitration evidence, including false-positive boundaries;
- framing and source-span rules;
- the supported subset and explicit postponements;
- malformed, truncated, unsupported, cancelled, and resource-limit semantics;
- maximum reads, output nodes, recursion/repeat bounds, and large-file behavior;
- whether a scanner/detector/analyzer is required or existing DSL is sufficient;
- compatibility and package-version consequences; and
- the exact tests and fixtures that will prove the decision.

If the current DSL or runtime cannot express the required semantics, stop after
recording the probe and its original error. Do not silently enlarge the core
contract.

### Step 3: Add the format specification

Use an official rule package unless the ADR explicitly proves that the change
is a format-neutral capability. A new package normally contains:

```text
src/rules/official/<package-id>/rule.toml
src/rules/official/<package-id>/src/*.svfmt
src/rules/official/<package-id>/docs/en/*.md
src/rules/official/<package-id>/docs/zh-CN/*.md
src/rules/official/<package-id>/tests/*
```

Register the package in `src/rules/CMakeLists.txt` and the relevant Qt
resource list. The manifest, entry point, detector name, documentation paths,
and package version must agree with the ADR and tests.

If the task changes the public DSL contract, update both:

```text
docs/format-language/README.md
docs/zh-CN/format-language/README.md
```

The language reference must cover syntax and static rules, runtime/source
coordinates, diagnostics and recovery, resource limits and cancellation,
compatibility/deprecation, and valid/invalid examples. C++ behavior or an
example alone is not a public language contract.

### Step 4: Add detection or integration only when required

Use the smallest layer that owns the behavior:

- `.svfmt` and the official package own format syntax and field semantics.
- `src/rules/` owns format-specific detection, framing, scanning, and analyzer
  orchestration when the DSL cannot discover boundaries by itself.
- `src/app/` owns format-neutral selection, presentation, and user-facing
  labels. It may not parse format bytes.
- `src/core/` owns source access, coordinates, bounded execution, cancellation,
  diagnostics, and format-neutral models.
- `src/tools/` owns `svtool` commands and probes.

When a capability is missing, first create a scratch probe and run
`svtool rule check`. A core, DSL, or public API change requires its own ADR
scope and must not be hidden inside a format-consumer commit.

### Step 5: Build evidence with fixtures and tests

Fixtures must be generated by a checked-in script or deterministic builder;
agents must not hand-edit bit offsets or claim coverage from a diagram. At
minimum, cover the format's real boundaries:

- one minimal valid sample;
- one representative valid sample for each advertised profile;
- truncated header and truncated payload/chunk;
- malformed lengths, offsets, alignment, or nesting;
- unknown or skippable chunks/boxes;
- unsupported but recognizable variants;
- detector false positives and ambiguous candidates;
- a large or sparse source that exercises the resource bound; and
- a follow-on valid unit after a malformed unit when recovery is promised.

Every fixture used as evidence must be named in the ADR and the corresponding
test. Add rule checks, analyzer tests, application tests, and fuzz coverage
only where the new behavior reaches that layer.

## 3. Version and Identity Rules

- A new format receives a new stable package ID; do not reuse an existing
  package or format identifier.
- Any change to decoding output or any `rule.toml` field, including `depth`,
  changes package content and requires a package version bump.
- Preserve exact package ID, version, content hash, and entry-point identity in
  session and diagnostic contracts.
- Never fall forward to another installed package version when the requested
  identity is missing or conflicting.
- Keep format semantics in rules and format-specific rule runners. Do not
  encode FourCCs, magic values, chunk taxonomies, or codec-specific branches in
  format-neutral core code.

## 4. Allowed and Forbidden Changes

### Allowed

- a new or revised official rule package, its manifest, DSL, bilingual package
  docs, and package tests;
- a format-specific detector, scanner, or analyzer under `src/rules/`;
- format-neutral application wiring required to expose a new entry point;
- a capability-only DSL/core change with a separate ADR and probe evidence;
- deterministic fixture generators, fuzz targets, CMake/resource registration,
  and focused regression tests;
- bilingual ADRs, format-language references, and implementation-plan records;
  and
- CI additions that verify the new format without weakening existing gates.

### Forbidden

- parsing format bytes in `src/core/` or Qt widgets;
- adding a format name, FourCC, magic number, or container taxonomy to a
  format-neutral core API;
- native executable code, scripts, network access, process access, dynamic
  dependencies, or symlinks inside a rule package;
- changing an existing format's behavior without an ADR, package-version bump,
  regression fixture, and explicit migration note;
- replacing exact rule identity with path-only, package-ID-only, or
  version-only lookup;
- making FFmpeg or another external tool a runtime dependency;
- deleting or weakening existing tests, warning gates, sanitizer gates,
  resource bounds, cancellation, or hosted matrix checks;
- skipping the English specification because a Chinese explanation exists; or
- marking the task complete while any required ADR, companion document,
  fixture, test, verification result, or plan entry is missing.

## 5. Required Verification

Before the task can be accepted, run the checks that apply to the changed
layers and record their actual output:

```bash
svtool rule check <every-new-or-changed-rule>
svtool analyze <representative-fixture> ...
ctest --preset dev -R "<targeted-tests>" --output-on-failure
cmake --preset dev
cmake --build --preset dev
ctest --preset dev --output-on-failure
cmake --preset ci
cmake --build --preset ci
ctest --preset ci --output-on-failure
cmake --preset sanitize
cmake --build --preset sanitize
ctest --preset sanitize --output-on-failure
git diff --check
```

Also run the fixture generator and the relevant fuzz target or deterministic
fuzz replay. Hosted CI must pass on every affected platform. Record run IDs,
job IDs, test counts, sanitizer status, and any non-blocking platform notice
in `docs/implementation-plan.md`.

## 6. Commit and Review Shape

Use the existing trunk sequence:

1. `docs(<scope>): specify ...` — bilingual ADR and normative docs;
2. `feat(<scope>): ...` — implementation and tests together;
3. `docs(<scope>): record ...` — verification evidence and plan update.

An independent review is required when the task changes the DSL/core contract,
cross-layer navigation, session/schema identity, resource or cancellation
semantics, or a fixed audit gate. The review is a gate, not a substitute for
the required tests.

## 7. Copy-Paste Agent Prompt

Use this prompt when assigning a new format task:

> Add support for `<FORMAT>` under `docs/format-extension-contract.md`.
> Treat the contract as a completion gate. First inspect the current plan,
> existing rule packages, ADR numbering, and the real source/test boundaries.
> Before code, write the next bilingual ADR and the English/Chinese format
> documentation. State the normative specification, package/entry-point
> identity, detector/framing model, supported subset, postponements, malformed
> and truncation semantics, resource limits, and exact fixture/test matrix.
> If the current DSL or runtime cannot express the format, stop after a
> scratch `svtool rule check` probe and report the original error with
> `file:line`; do not change core or DSL implicitly.
>
> Keep format semantics in the official rule package and `src/rules/`.
> Change `src/app/` only for format-neutral integration and labels; change
> `src/core/` only under a separately scoped capability ADR. Add deterministic
> fixtures, targeted tests, fuzz coverage where applicable, CMake/resource
> registration, and package-version updates. Run the full dev/ci/sanitize
> matrix, hosted CI, `git diff --check`, and update
> `docs/implementation-plan.md` with actual evidence. The task is incomplete
> until ADRs, bilingual docs, tests, verification records, and the plan entry
> all exist.
